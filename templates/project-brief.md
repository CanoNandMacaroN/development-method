# 项目 Grill 的问题范围

这张清单用于选问题，不是要用户逐格填表。AI 先查现有材料，按问题依赖分轮访谈；只讨论当前项目尚未明确的部分。开发方法、工具配合、提交与审查习惯沿用通用规范。

| 要弄清楚什么 | 对项目起步文档的影响 |
|---|---|
| 谁在什么场景遇到什么问题 | 写目标用户、主要价值，以及不解决的问题 |
| 用户从进入到得到结果的完整过程 | 决定首个可体验的小阶段；用真实例子说明成功和失败 |
| 首阶段与后续想法的边界 | 当前规格写细，后续进同一 backlog；避免一次设计全部未来功能 |
| 核心概念、对象、关系与规则 | 建立项目词汇和产品不变量；存在中英文需求时配对命名 |
| 数据从哪里来、存在哪里、谁能改 | 决定导入、保存、同步、离线、备份恢复、删除和权限；只深入适用项 |
| 对接哪些系统、插件或外部服务 | 明确兼容版本、认证、成本、限额及可替代方式 |
| 怎样表现，以及需要哪些语言和平台 | 确定交互、可访问性、本地化、桌面/移动/浏览器或命令行范围 |
| 在哪里开发，实际运行在哪里 | 选择本地、服务器、容器或组合，明确测试与正式数据边界 |
| 已有代码、技术栈和必须遵守的约束 | AI 核对复用机会与现有实现，给方案及取舍；已有事实直接继承 |
| 怎样证明当前阶段达到目标 | 写可观察验收、异常和恢复案例、性能或容量要求及真人体验节点 |

每个影响范围或架构的问题记录：已确认选择、原因、代价、受影响部分和验证办法。尚不影响当前阶段的问题进入后续候选，不无限扩展本轮访谈。

最终将结论写入项目产品规格和必要的决定记录；当前小阶段使用[规格模板](feature-spec.md)。说明哪些是用户确认、哪些是已授权范围内的工程选择、哪些仍是建议。不给通用规范重新编号或再投一次票。
