# 用测试证明行为，用证据定位故障

规范版本：0.1.0。项目通过自己的开发适配说明采用本章。

测试要回答一件具体的事：什么条件下，用户或调用方应得到什么结果。调试则回答，实际结果为什么偏离预期。两者共用可重复的输入和明确的观察点，不能靠测试数量或一句“运行正常”相互替代。

本章用于行为明确的功能、缺陷修复和实现后的验证。默认先写能失败的行为测试，再实现并整理代码；探索性原型和简单修改按实际情况裁剪。AI 自主选择测试边界、工具和执行顺序，需要用户决定的是行为或授权范围中的空缺。

## 从行为和当前代码建立验证计划

开始时需要当前规格、修改范围、代码基线、可重复的数据样例，以及项目已确认的检查入口和运行环境。先找出本次变化会影响哪些观察结果，再选择测试层次。

以“给记录添加标签”为例，可以从三个样例开始：添加后重新打开仍保留；重复添加只有一个；保存失败后输入仍在且能重试。样例使用少量容易理解的数据。发生过的缺陷逐步加入回归集；性能目标需要另选有明确规模的数据，不能把小样例的速度外推到大数据量。

| 要证明的事 | 合适的验证位置 | 单独通过时仍不能证明什么 |
|---|---|---|
| 重复规则与输入判断 | 不依赖界面和外部服务的行为测试 | 实际按钮已接上，或数据真的保存了 |
| 保存格式与重新读取 | 真实存储适配器和隔离测试数据 | 宿主或界面的完整交互正确 |
| 从操作到结果的路径 | 应用入口、真实组装与必要界面流程 | 其他平台、外部账号或所有异常都已验证 |
| 外部服务协议与配置 | 指定环境中的实际连接 | 模拟失败、重试等分支已充分覆盖 |

单元测试适合较小的规则，集成测试验证多个部分连接后的行为，端到端测试从应用入口观察完整过程。名称不是保证：标为“集成”的测试也可能把真正存储全部替换掉。记录它实际经过了哪些边界。

每个阶段默认检查本次变化、受影响流程和少量核心回归。项目很小时可以全部运行；重要交付节点再按约定扩大范围。验证范围有判断依据，避免因为“想更放心”机械重复无关的整套检查。

## 测试先行，从可信的失败开始

一轮测试先行可以按下面的顺序完成。

1. 用一句话写清行为，例如“重复给同一记录添加同一标签后，重新读取仍只有一个标签”。
2. 准备最小输入，通过被测试的公开入口执行动作，再观察结果。
3. 在实现前运行用例，确认失败与这条行为有关。
4. 完成最小实现，让用例通过，并检查相关既有行为。
5. 清理重复和不清楚的结构，再运行受影响用例。

失败要能区分产品问题与测试环境问题。断言发现两个重复标签，说明测试确实看到了规则缺口；测试框架未启动、路径错误或依赖缺失，只能说明测试还没有成功执行。新增入口尚不存在时，可先建立足以调用的最小结构，再确认用例能在行为断言处暴露缺口。

如果新增用例在未改业务代码前就通过，先判断现有实现是否已经满足需求，或用例是否没有经过预期路径。不要为了制造一次失败去破坏正确代码。修复既有缺陷时，保留能复现原问题的失败结果，使后续通过具有可比较的依据。

按行为逐个补充用例，比一次生成大量与实现同构的测试更容易发现问题。测试失败时先读实际结果，不立即修改期望值去迎合当前实现。

## 断言用户能观察到的结果

一个行为测试通常分为准备条件、执行动作、核对结果。准备代码应让读者容易看出为什么会触发这个情况；必要的辅助函数可以复用，但不要把关键前提藏进复杂的测试工厂。

标签例子的断言可以比较两种写法：

| 写法 | 能说明什么 |
|---|---|
| 断言“保存函数被调用一次” | 说明发生过一次调用，不能证明保存了正确对象和内容 |
| 添加标签后，通过独立读取核对目标记录；失败时核对输入和提示 | 能观察保存结果与失败承诺，但仍要说明使用的是哪种存储 |

调用次数在去重请求、资源释放等明确协议中可以是必要断言，但通常不能替代结果。重构内部函数不改变行为时，测试应尽量继续成立；如果大量测试只因私有函数改名而失败，说明它们可能绑住了实现形状。

对异步行为，控制请求完成顺序、时间来源或外部响应，在确定的状态上等待。比如先发出记录甲的保存，再打开记录乙，最后让甲的请求完成，检查乙的界面没有被旧结果污染。任意增加等待时间会让测试变慢，也未必消除竞态。

错误路径应观察影响，而不只检查抛出了异常。保存失败以后，原数据是否完整、输入是否保留、重复点击是否受控、下一次尝试是否可行，都取决于具体行为约定。选择与本次修改相关的风险，不要求每个小功能覆盖所有技术异常。

## 模拟依赖要保留真实问题

模拟依赖，也称 mock 或测试替身，用于控制外部条件。它适合稳定触发断网、慢响应、保存失败等难以重复的情况；它不能证明被替换掉的真实组件已经工作。

一个可信的替身应按输入产生可观察结果。例如，文件写入替身可以保存收到的内容供断言核对，或在指定写入阶段失败。若替身无论收到什么都返回预先写好的“成功、标签已保存”，测试很容易验证到自己准备的答案。

特别检查三个连接点：

- 实际应用启动时使用哪个实现，是否把测试替身带入了真实入口。
- 调用方传出的目标和数据，是否符合真实依赖接受的协议。
- 保存后的读取是否独立，是否只是从同一个内存对象取回刚写入的值。

因此，去重规则可以使用内存存储快速验证；证明文件持久化时则应写入隔离文件，重新创建读取对象再核对；证明宿主体验时，还要从宿主实际入口操作。三份结果各有价值，分别记录。

外部接口尽早完成首次实连。之后在相关接口、配置或运行条件变化时，以及约定的重要交付点再次实连；其余日常检查尽量可重复。记录采用的接口版本和实际验证范围，不能把某个模拟响应通过写成外部服务实连通过。

## 测试本身也需要检查

当一个重要用例总是通过，却与人工观察冲突时，先检查它是否真正执行了断言、异步动作是否被等待、测试入口是否选中了该用例，以及失败是否会正确传到运行结果。

可以在隔离的测试环境中注入一个已知故障，观察用例能否发现，比如让保存返回失败，验证界面没有显示成功。对于关键规则，也可以临时撤去目标修复来验证回归用例确实失败，然后恢复改动。此类验证针对尚不可信的覆盖，不需要对每个低风险测试重复做一套实验。

测试必须保留自己的退出结果。被跳过、没有选中用例、工具中断或缺少运行条件，都不能被汇总成通过。遇到不稳定测试，先找不稳定的输入或时序，保留原失败；多次重跑中恰好有一次成功，并没有解释前几次失败。

## 调试时一次检验一个有区分力的假设

调试从复现开始，而不是从修改开始。先记下预期、实际、最小输入、步骤、发生频率和环境身份，再找最早出现偏差的位置。能稳定复现的用例就是后续修复的起点。

假设出现“标签保存成功，重新打开却消失”，可以按证据逐步检查：

| 假设 | 有区分力的观察 | 观察结果怎样改变下一步 |
|---|---|---|
| 保存只改了界面内存 | 保存后查看隔离存储中的实际内容 | 没有标签时，继续查保存调用；已有标签时转向读取路径 |
| 写到了错误的记录 | 比较发起动作时的目标与实际写入目标 | 目标不同则检查上下文绑定；相同则排除这个假设 |
| 读取或展示丢掉了字段 | 分别查看存储读取结果与界面接收的数据 | 在首次缺失的边界定位转换或组装问题 |

一次实验尽量只改变一个有意义的条件。记录结果后保留或排除假设，再选择下一次观察。输出几百行无关日志，往往比核对一个目标身份更难定位；需要加诊断时，只记录能区分当前假设的信息。

同样的输入与环境下重复相同失败，不算新证据。连续尝试没有缩小范围时，停下整理已经排除的假设、尚缺的观察和下一步成本。涉及关键技术路线的不确定性，可以转入有投入上限的探索；达到边界后交付现有证据与选项，不能无限试改。

缺少环境、权限或外部连接时，说明究竟缺哪一个条件；其他可独立验证的工作继续进行。不要把“无法复现”直接等同于“问题不存在”，也不要用扩大权限、全局重装或无依据升级替代定位。

## 修复要回到最初的失败

找到原因后，优先做针对原因的最小修复。先让原失败用例通过，再检查相邻行为和受影响的真实入口。修复涉及存储时，重新读取；涉及异步归属时，重现完成顺序；涉及界面时，检查实际交互。

能够解释的修复记录应包含：触发条件、错误发生的位置、为何旧代码会产生该结果、修改怎样消除原因、哪个回归用例防止再次出现。暂时的绕行办法应标明限制与后续处理条件，不能改称根因已经解决。

原始缺陷输入适合保留时，将最小可公开或可授权使用的版本加入样例。去掉无关内容，使后来的人能够理解它为何触发问题，而不必重新读取一段很长的聊天或日志。

## 留下可以复核的验证记录

记录应足以让下一位执行者找到源码和重跑入口，不要求把所有原始输出复制进文档。

| 字段 | 记录内容 |
|---|---|
| 对象 | 任务、行为或缺陷，以及对应规格位置 |
| 源码与环境 | 固定源码身份、未提交差异情况、相关工具和运行环境版本 |
| 输入与入口 | 数据样例及版本、实际执行的项目检查入口 |
| 结果 | 通过、失败、未执行或条件未满足，并写清覆盖范围 |
| 证据 | 必要断言、失败与修复后的对比、报告或截图位置 |
| 剩余事项 | 尚缺的条件、未覆盖场景与继续验证的方法 |

单元、存储集成、真实应用和外部实连分别报告。结果有足够证据后，再按[审查与集成](review-and-integration.md)检查实现是否完整满足规格；审查通过也不会补出一份尚未执行的运行结果。
