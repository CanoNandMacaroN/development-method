# 开发原则与完整流程

本方法以可体验的小成果推进。整体目标、边界和关键架构先明确，当前要做的闭环写到可以实现和验收，后续功能随着反馈细化。专业程度体现在清楚的判断、可靠的实现和可信证据，不以文件数量或流程长度衡量。

## 共同的工作方式

人负责产品取舍，以及会影响长期架构、数据保存、权限、费用和外部交付范围的决定。AI 负责已确认范围内的实现细节、测试、局部整理和修复。遇到可查的事实，AI 自行查证；只有目标、取舍或授权确实未定时才提出问题。

一个闭环围绕完整的使用过程，例如“添加标签，保存，重新打开还能看到”。底层准备可以单独交付，但要说明实际验证的是技术能力，不把它当成用户功能已可用。

行为明确的功能与缺陷优先测试先行。探索性原型先回答一个具体问题；简单文字或可逆的小改动采用相称的检查。选择例外时说明理由和实际验证方式，不为了形式增加没有意义的测试。

默认最多同时运行两个子代理，主代理负责本轮结果。独立分析、实现和审查共用这个额度；没有可分离的工作就不必开满。并行实现使用隔离工作副本，各自有明确范围，组合后的行为仍要验证。

## 一次工作的完整顺序

1. **理解当前任务。** 读取当前目标、适用规范和相关代码；区分新增需求、缺陷、探索、简单修改。确认当前文件和分支状态，识别已有改动及其他人的工作。
2. **把目标写成可检查的行为。** 明确使用者、起点、结果、失败时保留什么。只追问会改变方案的歧义，给出推荐与代价。
3. **找到实现位置。** 追踪真实入口、数据权威和调用链，查现有能力及技术文档。关键可行性未知时先做有投入上限的验证，不用假设承诺完整功能。
4. **准备当前闭环。** 写清修改范围、依赖、验收实例、执行环境，以及哪些结果需要用户体验。需要并行时先确定接口与各自范围。
5. **实现并持续验证。** 每次推进一个行为；取得可信失败后做最小实现，再检查通过。记录出现的新事实；新的产品想法先进入候选，明确的纠正则及时调整当前工作。
6. **独立审查并集成。** 实现者自查后，另一审查者根据固定代码版本检查需求和实现。核实发现并修正，再验证合在一起的结果。
7. **交付并留下可接续材料。** 报告变化、理由、影响、实际验证和限制；更新当前状态，记录版本。已约定需要用户体验的节点等待反馈，其余已授权工作可以继续。

每一步可以很短。一个已知错误可能只需要几段任务记录、一项回归和一个修复；一次跨存储格式的变更需要更详细的设计与验证。裁剪的是记录和步骤的规模，完成判断仍要与实际目标一致。

## 什么情况下继续，什么情况下停下来

| 情况 | 下一步 |
|---|---|
| 实现细节明确且在已定范围内 | 自主处理，完成后解释主要选择 |
| 发现新的产品行为或关键取舍 | 给出具体方案及代价，等待相应决定；独立工作可继续 |
| 工具缺失，但有同等能力的已允许替代入口 | 核实替代能证明什么，记录后使用 |
| 缺少真实验证条件 | 完成可独立验证的部分，保留相关验收缺口 |
| 某项探索到达约定投入上限 | 收束证据和结论，说明可选路线，不原样重复尝试 |
| 当前验证失败 | 定位失败原因，修复受影响部分；不更改预期来掩盖缺陷 |

## 怎样判断进度

代码实现、验证通过、可交付和已发布是不同事实。状态记录写明范围，例如“保存与重开已在测试环境验证，外部登录条件尚缺”，不要只写“完成 90%”。测试数量和构建成功只能证明各自覆盖的内容。

本地可以保留过程提交；主线按完整功能或修复组织清楚的汇总记录。闭环完成审查与验收后再向已授权远端同步。普通版本汇集一组相关变化，提交或推送不自动表示发布。

可以带着不影响当前验收的维护欠账交付，但要记下具体代价和处理触发点。例如“接入第三种输入格式前统一解析逻辑”，比“以后重构”更容易执行。

## 给用户怎样的说明

交付说明回答四件事：为什么这样做、有什么代价、影响哪里、如何验证。需要时沿真实代码解释一条完整过程，代码细节按需展开。说明的目标是让用户知道以后从哪里接着做，不强制把每次开发变成课程。
