# 把一个使用过程做成可靠的实现

规范版本：0.1.0。项目通过自己的开发适配说明采用本章。

拿到一个功能后，先弄清用户会从哪里开始、哪些数据会改变、怎样看出成功，再沿着这条路径实现。一个阶段可以很小，但应让人体验到完整结果。只写好了数据类型或界面按钮时，记录的是这部分能力，不能据此宣布功能已经可用。

本章用于新增功能、修复缺陷和局部重构。行为明确时，结合[测试与调试](testing-and-debugging.md)先写失败用例；完成后进入[审查与集成](review-and-integration.md)。模块拆分、测试边界和局部重构由 AI 在已确认范围内决定，不需要逐项向用户申请。

## 开始前，把输入收齐

开工所需的信息不一定分成很多文件，但应能回答下面的问题。

| 输入 | 需要知道什么 | 信息不完整时怎么办 |
|---|---|---|
| 当前任务与行为规格 | 用户要完成什么，正常结果、重要失败和本轮范围是什么 | 涉及产品行为的空缺提出具体情境；纯实现细节按已有约定处理 |
| 项目适配说明 | 代码入口、运行环境、检查入口、目录边界和所采用的规范版本 | 核对实际文件与可用工具，标明尚未验证的入口 |
| 现有实现 | 从用户操作到保存、重新读取的路径，已有约束和可复用能力 | 沿真实调用关系阅读，不把目录名和旧报告当作实现证据 |
| 工作基线 | 当前分支、源码身份、已有未提交改动及本轮写入范围 | 保留他人改动；并行写入使用隔离工作副本 |
| 验证计划 | 本次行为、受影响流程、核心回归和需要真实环境的部分 | 先确定怎样观察结果，避免写完后才发现无法证明 |

后文使用一个假设例子：给记录添加标签。假设已确认的行为是，重复添加同一标签不会出现副本；保存成功后重新打开记录仍能看见标签；保存失败时保留输入并说明失败。这里的选择只是演示材料，不替其他项目决定标签的大小写、长度或共享规则。

## 先找到真正执行的代码

阅读从项目入口说明开始，然后跟踪一个具体动作。仓库若已有可用的代码索引，先用它定位符号和调用关系，再核对当前源码；没有索引时，用文本检索找到入口及调用方。索引结果可能落后于工作区，最后以实际读取的文件为准。

以添加标签为例，可以按下列顺序记录路径：

```text
用户点击添加
  → 读取本次输入和目标记录
  → 判断这次添加是否有效
  → 调用记录的保存能力
  → 根据保存结果更新界面
  → 关闭后重新读取记录
```

每经过一步，查看它的输入来自哪里、输出由谁使用、失败怎样传回。尤其要看组装代码：真正运行时注入的是文件存储，还是测试内存对象？界面事件有没有连接到已经写好的业务功能？“有一个保存函数”只能证明函数存在。

优先阅读当前路径、相邻测试和项目约定。遇到不熟悉的实现，可以继续追一层调用；没有必要一开始浏览整仓，也不应只看搜索摘要就修改跨模块协议。发现规格和源码不一致时，分别记录预期行为与实际行为，再判断这是待修复缺陷还是需要用户决定的变化。

## 把当前使用过程拆成能验证的小步

小步围绕可观察行为展开。标签功能可以先完成“添加一次并在重新打开后保留”，再处理重复添加和保存失败。每一步都接在同一条真实路径上，使后续测试能复用已经成立的基础。

执行顺序通常是：

1. 为当前明确的行为写一个能区分正确与错误的用例，确认现有实现为何失败。
2. 用最少的改动让它通过，同时遵守已经明确的数据和接口约束。
3. 加入下一个关键边界，重复实现与验证。
4. 整理重复和不清楚的职责，再跑受影响检查。
5. 用真实应用入口走通这段使用过程。

“最少改动”不意味着硬编码测试输入，也不意味着略过规格已经要求的失败处理。它限制的是暂时用不到的扩展：一个标签功能还不需要因为未来可能有更多元数据，就先搭建通用规则平台。

若关键技术是否可行还不知道，把它单独作为有边界的探索：写明要回答的问题、可接受的投入和成功或失败证据。探索得到“不成立”是有效结论，但不把探索样例算成正式功能交付。

## 按职责组织代码，让变化有明确去处

拆分的目的，是让读者知道一条规则在哪里改、改动会影响谁。小功能可以在少量文件内完成，不要求每种职责都新建一个目录、类或接口。

| 职责 | 标签例子中的工作 | 应避免的混杂 |
|---|---|---|
| 界面或外部入口 | 获取标签输入与目标，展示正在保存、成功或失败 | 同时决定磁盘格式、直接改多处数据 |
| 行为判断 | 判断重复、无效输入和允许的操作 | 为了判断重复而启动界面或连接外部服务 |
| 存储或外部适配 | 按明确协议读取、写入并返回结果 | 把保存失败转换成“成功但没有变化” |
| 应用组装 | 选择实际实现，连接入口、业务和存储 | 让测试替身意外成为真实应用的默认实现 |

接口先说明“要完成什么、给什么输入、可能返回什么结果”，再选择技术形状。只有当边界能降低耦合、支持必要替换或使重要行为可测试时，才值得增加抽象。给每个函数配一个同名接口，通常只增加查找成本。

可观察的改进是：更换保存方式时，标签重复规则无需跟着修改；测试重复规则时，无需启动整个应用。需要留意的信号是：修改一个标签规则，要同时改界面、存储、缓存和多份相同判断，且没有地方能说明谁说了算。

命名应表达业务动作和对象。写清“给哪条记录添加哪个标签”，比依赖当前选中对象的泛用“更新数据”更容易检查。代码沿用项目已确认术语，不临时制造相似但不同的概念。

## 明确状态归属与副作用

副作用是写文件、发送请求、修改外部状态等会影响函数外部的动作。让规则计算尽量独立，把实际写入集中在清楚的边界，测试和排错都会容易一些。

标签编辑至少要区分输入草稿、保存中的操作和已经确认保存的数据。哪个数据源决定持久结果，应在项目的数据约定中明确。界面为了即时反馈显示了标签，不意味着保存已经完成。

设计一个写入动作时，顺着它回答这些具体问题：

- 目标在什么时候确定，执行中切换页面会不会改到另一个对象？
- 保存成功的依据是什么，失败以后保留哪些输入？
- 重复点击或重试，会不会产生重复结果？
- 一个动作涉及多处写入时，如何发现部分完成并恢复到约定状态？

单次原子写入能满足要求时，优先使用现有存储能力。确实涉及多处状态一致性时，再设计事务或恢复协议；不要为了让简单功能显得完整，强行加入一套通用事务框架。

错误需要保留足以定位问题的信息，并在用户能理解的层次说明结果。保存失败时，界面可以说明“标签尚未保存，输入已保留”；开发记录则保留失败阶段与必要诊断。避免捕获所有异常后返回空值，让调用方无法区分“没有标签”和“读取失败”。

## 异步结果必须找到原来的目标

异步动作完成时，用户可能已经切换对象、修改内容或离开页面。发起操作时应固定必要上下文，完成时再核对结果是否仍可应用。

假设用户给记录甲添加标签，保存尚未返回便打开记录乙。正确结果是标签写入甲；乙的界面不会因为甲的请求返回而显示错误标签。为此，操作需要保存甲的身份，界面更新还需要判断自己当前展示的对象与请求是否匹配。具体采用请求标识、版本号还是其他方式，由项目实际状态模型决定。

取消也要说明取消了什么。停止等待界面结果、发出网络取消请求、保证外部写入未发生，是不同承诺。写入已经发生时，不能仅关闭提示框就报告“已撤销”。如果功能需要真正撤销，应在行为规格中规定相应动作和结果。

清理监听器、定时器和临时资源时，按创建者与生命周期配对。对较慢操作，用可控的完成顺序测试“旧结果晚到”，比依靠固定等待时间更容易复现问题。

## 复用成熟能力，并保留清楚的接入边界

满足需求且没有明显成本劣势时，优先复用成熟组件。选择前查看它实际支持的行为、维护情况、许可、依赖和替换成本；涉及具体库或接口的用法时，按项目约定核对当前文档与采用版本。

接入前先跑通一个最小实例，再把组件连接到本项目的真实入口。仅运行组件自带示例，不能证明标签已经写入本项目的数据。需要修改上游时，记录原版本、必要差异及原因，使后续升级能够区分项目适配和无关改动。

封装应隐藏确实会影响调用方的差异，比如保存结果、错误或数据格式；不必把组件的每个函数机械转发一遍。复用整个项目是否值得，则应比较本轮真正需要的能力与额外维护负担。

## 实现中持续重构，欠账写明触发条件

当行为测试已经保护现有结果时，可以在实现过程中调整命名、合并重复、缩小接口和移动职责。重构不只发生在审查后。尽量把行为变化和结构整理分成可理解的小步，便于发现是哪一步改变了结果。

超出当前目标但不影响本轮验收的维护问题，可以记录后续处理。记录要说清具体代价与触发条件。例如：“两个导入入口暂时各有格式转换；新增第三个入口前统一转换能力，否则规则容易不同步。”只写“以后优化架构”无法指导下一次开发。

已经造成错误结果、数据丢失或验收失败的问题应按缺陷处理。需要改变产品行为、长期架构、数据保存方式或新增运行服务时，把原因、代价、影响和验证方案交给用户决定；局部实现选择由 AI 继续完成。

## 交给审查的产物与证据

这一阶段应留下能够运行的改动、相应测试、必要的接口或适配说明，以及与实际源码对应的验证记录。对用户的说明聚焦为什么这样实现、影响哪些流程、怎样验证和仍有哪些限制，代码细节按需展开。

提交审查前，从真实入口走一遍当前使用过程；检查结果是否能跨重新读取保留，重要失败是否保持约定状态，再检查本次变化、受影响流程和少量核心回归。环境未具备的部分写明具体缺口，已经可以独立验证的部分继续完成。

如果验证失败，保留失败输入与结果，按[调试步骤](testing-and-debugging.md#调试时一次检验一个有区分力的假设)定位原因。行为本身未明确时提出具体问题；技术路线被证据否定时更新方案；不通过缩小断言或删掉要求来获得通过结果。
